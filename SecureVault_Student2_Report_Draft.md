## 7.2 Protecting Document Contents

### Our choice and the alternatives

We use **AES-128-GCM**, a dedicated authenticated-encryption mode, for each document. It encrypts the document and produces an authentication tag. The public metadata is encoded unambiguously and passed as **additional authenticated data (AAD)**. The filename and file type are also inside the encrypted, authenticated payload. In the current integrated application, the server additionally stores a clear filename to display document lists. On download, the client must compare this clear name (and the name from the list when applicable) with the authenticated filename before saving. The server therefore learns the filename; we must not claim that it is hidden.

We considered composing AES-CTR and HMAC-SHA-256 ourselves. If using that design, the correct order would be **Encrypt-then-MAC**: encrypt first, authenticate the nonce, ciphertext and relevant metadata, and verify the MAC before decrypting. Our running document path instead uses GCM, so it does **not** have a separate document HMAC key or a separate HMAC pass. CCM was another possible authenticated-encryption mode; we selected GCM because our code uses its direct AAD and tag interface. The report must name PyCryptodome's AES-GCM as a library component. An AES implementation elsewhere in the repository must not be counted as the AES used for documents unless the actual call path uses it.

### Keys and nonces

Each new document receives **one independent 128-bit document key, K_doc**, generated by the operating-system random source on the client. One GCM encryption with this key uses a 96-bit random nonce. For a recipient, the client generates an ephemeral P-256 ECDH key pair, derives a distinct wrapping key with HKDF-SHA-256 and a fresh salt, and uses AES-128-GCM to encrypt K_doc for that recipient. The ECDH and ECDSA long-term private keys have separate purposes and are encrypted at rest using password-derived keys. The server gets the encrypted document and wrapped document key, not K_doc in plaintext.

The document nonce comes from `os.urandom(12)`. The intended rule is **one fresh K_doc per encryption**, including replacement uploads. Because a freshly generated key is not reused, a process restart does not require a persistent nonce counter for that document key. The same reasoning applies to ephemeral wrapping keys only if the implementation really creates a new ephemeral ECDH secret and salt for each wrap. Random generation makes accidental repetition overwhelmingly unlikely; it is not an absolute mathematical guarantee. If the application ever encrypts a new version under an old K_doc, it must enforce nonce uniqueness across restarts before making that claim. Verify the update path and document/version-key policy in the final integrated code.

The client calls `verify_document` to check the GCM tag before using plaintext. It checks document ID, expected owner when supplied, minimum version, and authenticated filename before writing the result. The file is written to a temporary file and moved into place only after verification. Our earlier unit run passed **32 document tests**; targeted ciphertext and public-metadata tampering tests both passed. A client-level test of a modified network response and absence of an output file should be included in the final demonstration.

## 7.3 Public-Key Cryptography

SecureVault uses separate **P-256 ECDH** and **P-256 ECDSA** key pairs for each user. ECDH lets Layla protect a randomly generated document key so that only Omar's private ECDH key can unwrap it. ECDSA authenticates the signed share record and allows a third party holding Layla's valid certificate to verify that signature. P-256 offers about **128-bit classical security**, matching AES-128's intended security level. A P-256 public point in our uncompressed encoding is 65 bytes. This is a key-size comparison, **not** a measured speed comparison: before claiming ECC is faster than a finite-field alternative, add measured key-generation, agreement and verification times for explicit alternative parameters on the same machine.

The signed share record includes the document ID, sender, recipient, wrapped key, timestamp and version. It does not by itself demonstrate that the ECDSA signature covers the exact bytes of the encrypted document or the plaintext. To claim third-party proof of the *specific document contents*, the final design should sign or otherwise cryptographically bind a digest of the protected document to this share record, then show a third-party verification procedure. GCM authenticates bytes for people with K_doc but does not itself provide non-repudiation.

## 7.4 Trusting a Public Key

We selected a **small private Certificate Authority (CA)**. Its private signing key is kept outside the document server; clients are provisioned with the trusted CA public key. A certificate binds one username to separate ECDH and ECDSA public keys, with an issuer, serial number, validity interval and CA signature. The client checks the CA signature, validity, expected username and whether the certificate's public keys are the ones used for that registration or share. This blocks a network attacker from substituting an unsigned key for Omar's while leaving the pinned CA trust anchor intact.

At first enrollment, the client creates keys and a **signed enrollment request** as proof of possession of its ECDSA private key. The CA administrator validates this request, then independently checks the applicant's right to the username and compares the ECDH and ECDSA fingerprints received from the applicant before issuing a certificate. The administrator must check the fingerprints over an independent, trusted channel; copying them from the same request file provides no independent check. A manual `APPROVE` confirms that the procedure was performed, but the word alone is not evidence of identity. The CA therefore relies on the administrator's identity check and on protecting the CA private key. On first contact, Layla verifies Omar's certificate under the pinned CA public key and checks the expected name before wrapping K_doc to Omar's certified ECDH key. Layla and Omar do not need to compare full key fingerprints directly if they trust this CA issuance process.

We preferred this to trust-on-first-use because first-contact key substitution is in scope. Direct out-of-band fingerprint comparison is possible, but it requires every pair of users to coordinate a separate comparison. Our CA approach centralizes that manual check at enrollment; it does not eliminate human error or the need to distribute the authentic CA public key.

The CA and enrollment tests reported **27 passing** across certificate, issuance and signed-request suites; the integrated run showed stored certificates validating for the intended usernames, and a Layla-to-Omar document share and receive worked. Receiving the same share a second time was rejected as stale in that live session. This does not yet prove that document replay is rejected after a client restart.

## Related learning objectives and threat-model evidence

1. **Design and trade-offs:** GCM combines encryption and authentication; the custom Encrypt-then-MAC alternative would require independent keys and careful verification order. The CA binds usernames to keys and supplies first-contact trust. The report should explicitly list PyCryptodome AES-GCM and `argon2-cffi` Argon2id among library-provided cryptography, and count only custom components actually executed by the final application when evaluating the 70% requirement.
2. **Correct behavior:** Report the actual tests and results, including published test vectors for primitives written by the team, tamper rejection, certificate substitution rejection and end-to-end sharing. A passing primitive test does not automatically prove the integrated network path.
3. **Credential protection:** The server stores a separate random 16-byte salt and an Argon2id result per account. Recorded parameters are 128 MiB memory, three passes and one lane. Team benchmark figures previously reported around **255 ms per evaluation** for that configuration; rerun on the presentation machine and record the hardware, number of trials and measured result. If one attacker evaluation really takes 0.255 s on the measured reference device, 10,000 guesses for one account take about 2,550 seconds of that device's serial work. This is not a universal GPU cracking-time guarantee, and weak passwords remain guessable. Password-derived encryption also protects private keys at rest; the server must not receive plaintext passwords or unwrapped private keys.
4. **Threats and limits:** The attacker may read the stored database, alter traffic and replay objects. GCM detects edits to protected document bytes and bound metadata. CA certificates plus the sender's ECDSA signature authenticate a signed share, subject to the CA's issuance procedure. A replay of a share was rejected in one active client session. Two remaining issues require explicit fixes or limitations: `pickle.loads` on untrusted network input in the reviewed snapshot may execute attacker-controlled code before verification, and freshness for old document versions across client restarts has not been established. The JSON codec discussed later is a proposed change until implemented and tested in the merged folder.
5. **Design defense:** Be ready to explain why GCM verification occurs before writing, how fresh document keys prevent nonce reuse across restarts, why the CA administrator cannot rely only on typing `APPROVE`, and how a third party verifies a signature tied to the exact document rather than just its share envelope.

**Evidence status:** This is a defensible draft of what we observed, not a claim that all project requirements have been completed. Re-check the final code paths and tests, especially nonce/key reuse on updates, exact-content signature binding, persistence of freshness state, and removal of network `pickle.loads`.
